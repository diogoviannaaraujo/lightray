# The handshake

One round trip establishes a session: the client sends `INIT`, the host replies with
`RESPONSE`, and both sides derive the same traffic keys. There is no second round trip
and no negotiation beyond what those two packets carry.

The application supplies, out of band, a **pairing identifier** (`u64`) and a **pre-shared
key** (PSK). The pairing identifier is not secret; it tells a host which key to try. The PSK
MUST be exactly 32 bytes and MUST be generated by a cryptographically secure random source.

> **Why a pre-shared key at all.** The two endpoints belong to the same person and were
> introduced once, in an application flow this protocol does not define. Given that, a
> certificate chain buys nothing that a pairing secret does not, and costs a round trip
> and a trust store. The PSK also authenticates the very first packet, which is what
> lets the host reject unpaired traffic before doing any asymmetric work.

## Noise

The handshake is the Noise Protocol Framework's `NNpsk0` pattern with X25519, AES-256-GCM and
SHA-256 (revision 34 of the Noise specification):

```
Noise_NNpsk0_25519_AESGCM_SHA256

NNpsk0:
  -> psk, e
  <- e, ee
```

The client is the initiator and the host the responder. Lightray adds framing and nothing
else: a cleartext header on each handshake packet, a prologue, and the payloads. An
implementation MAY use any Noise library that supports this protocol name, a prologue, and the
explicit nonces of [packets.md](packets.md#protection). This section restates what such a
library does, so that no other document is needed to implement it.

> **Why Noise.** Version 0's handshake already had this shape: one ephemeral each, a PSK that
> seals the first message, and keys from the Diffie–Hellman result mixed with the PSK. Naming
> the pattern replaces a bespoke key schedule with one that has a published security
> analysis, libraries in many languages, and published test vectors, which the generator in
> [`tools/vectors`](../tools/vectors/README.md) checks its Noise code against.

### Primitives

| Noise function | Lightray |
|---|---|
| `DH` | X25519 as RFC 7748 defines it, including how it clamps a private key. Keys are 32 bytes. |
| `ENCRYPT(k, n, ad, plaintext)` | AES-256-GCM with the 32-byte key `k`, the nonce `0x00000000 ‖ n:u64`, and the associated data `ad`. The 16-byte tag follows the ciphertext. |
| `DECRYPT(k, n, ad, ciphertext)` | The matching AES-256-GCM open. It fails if the tag does not verify. |
| `HASH` | SHA-256. |
| `HKDF(ck, ikm, count)` | Noise's HKDF, where `HMAC(key, data)` is HMAC-SHA256 with the key first: `temp = HMAC(ck, ikm)`, then `out1 = HMAC(temp, 0x01)`, `out2 = HMAC(temp, out1 ‖ 0x02)` and, when three outputs are needed, `out3 = HMAC(temp, out2 ‖ 0x03)`. `0x01`, `0x02` and `0x03` are single bytes. |

The handshake state is a chaining key `ck`, a hash `h`, and a cipher key `k` with a nonce `n`
that increments after each `ENCRYPT` or `DECRYPT` and restarts at 0 whenever `k` changes:

| Operation | Effect |
|---|---|
| `MixHash(data)` | `h = HASH(h ‖ data)` |
| `MixKey(ikm)` | `ck, k = HKDF(ck, ikm, 2)` |
| `MixKeyAndHash(ikm)` | `ck, temp, k = HKDF(ck, ikm, 3)`, then `MixHash(temp)` |
| `EncryptAndHash(p)` | `c = ENCRYPT(k, n, h, p)`, then `MixHash(c)`; `c` includes the tag |
| `DecryptAndHash(c)` | `p = DECRYPT(k, n, h, c)`, then `MixHash(c)`: the hash takes the ciphertext, as it does when encrypting |
| `Split()` | `k1, k2 = HKDF(ck, ikm, 2)` with an empty `ikm`, zero bytes long |

### The steps

Both sides start from the protocol name, `Noise_NNpsk0_25519_AESGCM_SHA256`. It is exactly 32
bytes, the length of a SHA-256 hash, so it becomes the initial `h` directly, without hashing,
and `ck = h`.

The **prologue** is:

```
prologue = "lightray-v1" ‖ INIT[0..12)
```

`"lightray-v1"` is 11 ASCII bytes with no terminator. `INIT[0..12)` is the `INIT`'s cleartext
header: type, version, reserved and pairing identifier. Both sides use those bytes as they
appear in the `INIT`, so every cleartext byte of the `INIT` is authenticated, the reserved
bytes included.

The client builds the `INIT`:

1. `MixHash(prologue)`.
2. `psk`: `MixKeyAndHash(psk)`.
3. `e`: generate an ephemeral key pair; `MixHash(e.public)`; `MixKey(e.public)`.
4. `EncryptAndHash(payload)`.

The host opens it with the same steps, taking `e.public` from the packet and decrypting in
step 4. Nothing before step 4 needs a Diffie–Hellman operation: a host rejects an `INIT` sealed
under the wrong PSK with hashing and one failed AES-GCM open.

The host builds the `RESPONSE`, continuing from that state:

5. `e`: generate an ephemeral key pair; `MixHash(e.public)`; `MixKey(e.public)`.
6. `ee`: `MixKey(DH(e, re))`, where `re` is the client's ephemeral public key.
7. `EncryptAndHash(payload)`.
8. `Split()`.

The client opens it with the same steps, decrypting in step 7, and splits. `Split()`'s first key
is the client-to-host key and its second the host-to-client key.

Every `e` is mixed into the key as well as the hash; that is what Noise does in a handshake
with a PSK (section 9.2 of its specification). Each `EncryptAndHash` in the handshake runs with
`n = 0`, because the key changed in the step before it.

A client MUST open each `RESPONSE` on a copy of the state its `INIT` left, because steps 5
and 6 change the state before the tag is checked. A `RESPONSE` that fails to open then changes
nothing, and the client can try the next one. A client whose Noise library cannot copy a
handshake state can rebuild it instead: running the `INIT`'s steps again with the same
ephemeral key and payload produces the same state.

If `DH` fails, or produces 32 zero bytes, as it does when the other side's public key is a
low-order point, the packet counts as one that failed to open. A client discards the
`RESPONSE` and keeps waiting; a host discards the `INIT` without replying. Some X25519
libraries report such a key as an error, and others return the zero result; both mean the
same here.

> **Why the prologue covers the header.** Noise authenticates the prologue and the messages,
> and nothing else. The `INIT`'s header is sent in the clear because the host needs the
> pairing identifier to find the key, so it goes into the prologue. That binds the version and
> the pairing into every key the handshake produces: an `INIT` can't be replayed into another
> version or another pairing, even by an implementation that forgets to check the header, and
> the reserved bytes can be given a meaning later without an attacker being able to change
> them.

## INIT (`0x80`), client → host

```
type:u8 = 0x80
version:u8 = 1
reserved:u16                        written 0, ignored on receipt, part of the prologue
pairing_id:u64
--- the 12 bytes above are cleartext and part of the prologue ---
e[32]                               the client's ephemeral public key
ciphertext[max_datagram_size − 60]  the payload, sealed by EncryptAndHash
tag[16]
```

The datagram MUST be **exactly `max_datagram_size` bytes**, the size the client proposes
in its parameters. The sender MUST set don't-fragment on the socket.

A host MUST discard an `INIT` outside the 256–9000 byte range before attempting to open it,
and MUST discard one whose length does not equal the `MAX_DATAGRAM_SIZE` its parameters
declare.

> **Why the padding and the size check.** Two jobs at once. The padding makes the
> `RESPONSE` smaller than the packet that triggered it, so an attacker who spoofs a
> source address cannot use the host as an amplifier. And because the datagram is sent
> with don't-fragment at exactly the size the session will use, a path that cannot carry
> that size fails here, during a retried handshake, rather than after the session is
> up, where it would present as unexplained total loss of large frames.

### Payload

```
params_len:u16
params[params_len]                  parameter TLVs
padding[...]                        zero bytes to the end of the payload
```

The payload is `max_datagram_size − 60` bytes. The padding is inside the seal and is therefore
authenticated.

> **Why the padding is inside the seal.** Padding appended after the tag would be
> unauthenticated: an attacker could strip it, and a receiver could not tell where the
> ciphertext ended without a length field to trust. Inside, the ciphertext length is
> implied by the datagram length, and any tampering with the padding breaks the tag.

A receiver MUST verify that `params_len` does not exceed the rest of the payload, and MUST
ignore every byte after `params`.

## RESPONSE (`0x81`), host → client

```
type:u8 = 0x81
version:u8 = 1
e[32]                               the host's ephemeral public key
ciphertext[...]                     the payload, sealed by EncryptAndHash
tag[16]
```

The payload is:

```
session_id:u32                      chosen by the host, MUST NOT be 0
reset_token[16]                     see SESSION_UNKNOWN below
params[...]                         parameter TLVs, to the end of the payload
```

A `RESPONSE` MUST NOT be larger than the `INIT` that triggered it, and a host MUST
enforce this before sending.

A client MUST accept only type `0x81` and version 1. It MUST discard, and keep waiting, a
`RESPONSE` that is larger than its `INIT` or that fails to open, because anyone can send one.
A `RESPONSE` that opens came from a holder of the PSK. If its payload is shorter than the 20
bytes of its fixed fields, its `session_id` is 0, or its parameters are invalid, the client
MUST abandon the handshake and report the error to its application.

Once its handshake is complete, a client MUST ignore any further `RESPONSE`. Duplicates are
normal: a host answers each copy of a retransmitted `INIT` from its cache.

> **Why the session identifier is inside the seal.** Version 0 sent it in the clear and
> authenticated the cleartext as associated data. Noise authenticates only the prologue and the
> messages, and the prologue is fixed before the host has chosen anything, so a field the host
> adds in the clear could not be authenticated. Inside the payload it is both encrypted and
> authenticated. The client needs no cleartext identifier to match the reply: it has one
> handshake outstanding per host. The two cleartext bytes are not authenticated either, and
> need not be; a client accepts exactly one value of each, so there is nothing to alter.

## Traffic keys

`Split()` produces two 32-byte keys. The first is the **client-to-host** key and the second
the **host-to-client** key. Each seals every protected packet in its direction for the life of
the session ([packets.md](packets.md#protection)), starting at packet number 0.

Once it has split, each side MUST erase its ephemeral private key and the handshake state.
The handshake hash is not used for anything else.

A host MAY send protected packets as soon as it has sent the `RESPONSE`. They can overtake it,
so a client SHOULD keep up to 64 protected packets that arrive from the host's address while
its handshake is outstanding, and open them once it has the keys. Until then they MUST NOT
change any state.

> **Why the host doesn't wait.** When a relaunched app reconnects, the host sends the first
> frame right behind the `RESPONSE`, so that the app is back after one round trip, as fast as a
> resume. Waiting for the client to speak first would add a second one. On Wi-Fi a datagram
> can overtake the one sent before it; without the buffer, the start of that first frame would
> need repair.

## Parameters

`INIT` and `RESPONSE` carry parameters as TLVs:

```
type:u8
length:u16
value[length]
```

| Type | Name | Value | INIT | RESPONSE | Defined in |
|---|---|---|---|---|---|
| `1` | `SETTINGS` | The client's proposed settings; the host's applied ones | | | [modes.md](modes.md) |
| `2` | `TIMESTAMP` | `u64`, Unix time in seconds | REQUIRED | MUST NOT appear | [below](#replay-protection) |
| `3` | `CAPABILITIES` | What each side can do | | | [video.md](video.md) |
| `4` | `STREAM_TABLE` | Stream entries, 4 bytes each | REQUIRED | REQUIRED | [below](#stream_table-4) |
| `5` | `MAX_DATAGRAM_SIZE` | `u16` | REQUIRED | REQUIRED | [below](#max_datagram_size-5) |
| `6` | `RESUME_SESSION_ID` | `u32` | OPTIONAL | MUST NOT appear | [below](#taking-over-a-session) |
| `7` | `LIFECYCLE` | The session's timing | | | [session.md](session.md) |

`SETTINGS`, `CAPABILITIES` and `LIFECYCLE` are numbered here and defined, with whether each is
required, in the documents named. Until those are written, a receiver skips them as it would an
unknown type, and the worked example leaves them out. Type `8`, version 0's reset token, is
retired: the reset token is a fixed field of the `RESPONSE`.

TLVs MAY appear in any order. A receiver MUST reject the handshake if:

- a TLV of type 1–7 appears more than once;
- a TLV required in that packet is absent, or one that MUST NOT appear is present;
- a TLV's length is wrong for its type: `TIMESTAMP` is 8 bytes, `MAX_DATAGRAM_SIZE` 2,
  `RESUME_SESSION_ID` 4, and `STREAM_TABLE` a multiple of 4;
- a TLV's length exceeds the bytes remaining in `params`, or one or two bytes remain after the
  last TLV, too few for a TLV header.

A receiver MUST skip a TLV whose type it does not recognise, using its length.

To reject a handshake, a host discards the `INIT` without replying, and a client abandons the
handshake as described under `RESPONSE`.

### `STREAM_TABLE` (4)

A list of 4-byte entries:

```
id:u8
kind:u8
direction:u8
class:u8
```

The values are in [registries.md](registries.md#streams), and what they mean is in
[packets.md](packets.md#streams). The client proposes a table; the table in the `RESPONSE` is
authoritative, and the client MUST use it. A host MAY leave out streams it will not carry. It
MUST NOT add a stream or change an entry.

A receiver MUST reject the handshake if the table is empty, has more than 32 entries,
contains `id = 0`, contains a duplicate `id`, or names an unassigned kind, direction or
class. A client MUST also reject a `RESPONSE` whose table adds a stream or changes an entry.

> **Why a hard failure rather than skipping the entry.** A stream table both sides do
> not agree on exactly is worse than no session. Skipping an entry one side did not
> understand means the two ends silently disagree about what stream 4 is, and the first
> symptom is media arriving on a stream the receiver treats with the wrong class.

### `MAX_DATAGRAM_SIZE` (5)

A `u16` from 256 to 9000; see [packets.md](packets.md#datagram-size). In an `INIT` it is the
size the client proposes, and it MUST equal the length of the `INIT` itself. In a `RESPONSE`
it is the size of the session, and it MUST NOT exceed the client's.

## Replay protection

`TIMESTAMP` is Unix time in seconds. A host MUST reject an `INIT` whose timestamp
differs from its own clock by more than 30 seconds.

A host MUST additionally keep a cache of recently accepted `INIT` packets, keyed on
`SHA256(entire INIT datagram)`, holding at least 1024 entries for at least 60 seconds.

On receiving an `INIT` whose digest is already in the cache, a host **MUST resend the
identical `RESPONSE` it sent the first time**, and MUST NOT create a second session or take
over a session again.

> **Why the cached RESPONSE, and not a rejection.** A client that receives no
> `RESPONSE` cannot tell whether its `INIT` was lost or the reply was, so it retransmits
> the same `INIT`: the same bytes, the same ephemeral. A host that treats the repeat as
> a replay and drops it makes a lost `RESPONSE` unrecoverable: every retry is dropped
> for the same reason, and the handshake never completes on a link that drops one
> packet. Replaying an `INIT` must not create a session; it must reproduce the answer.
>
> The cache is also what makes the timestamp window safe to keep short. The window bounds
> how long a captured `INIT` is useful at all; the cache ensures that within the window a
> repeat is answered rather than acted on.

A host MUST look an `INIT` up in the cache only **after** it opens, so that unauthenticated
traffic cannot evict cache entries, and **before** checking its timestamp. A duplicate is then
answered from the cache even if its timestamp has since left the window, so a client
retransmitting near the edge of the window still gets its answer.

A host SHOULD bound the number of concurrent sessions and MUST have some limit.

## Version mismatch

A receiver that sees an unimplemented version MUST silently discard the packet and
SHOULD count it. It MUST NOT reply.

## Taking over a session

A client MAY name, in `RESUME_SESSION_ID`, a session it held before. If the host still holds
that session for the same pairing, **whether active or parked**, it MAY take it over for the
new handshake:

- the session identifier survives, and so do the host's capture and encoder, which is the
  point: the first frame can come from a warm pipeline;
- the new handshake negotiates like any other, and its `RESPONSE`'s stream table, datagram
  size and parameters apply from then on;
- the traffic keys, the packet numbers and replay windows in both directions, and the
  reliable message sequences are replaced by the ones this handshake starts;
- the peer address becomes the source address of the new `INIT`.

[session.md](session.md) says what else survives and what the host sends first.

If the host does not take the session over, it allocates a new session identifier and the
client starts fresh. The client learns which happened from the `session_id` in the
`RESPONSE`.

Once a session is taken over, packets under its old keys no longer authenticate.

> **Why an active session can be taken over.** A client whose app was killed comes back with a
> fresh handshake, and its session is usually still active on the host, which has not yet
> noticed the silence that would park it. Taking it over lets the relaunched app reach its warm
> encoder in one round trip, as fast as a resume, instead of waiting for the park or starting
> cold. Only a holder of the pairing's PSK can take over its sessions, and a replayed `INIT` is
> answered from the cache and takes nothing over.

## SESSION_UNKNOWN (`0x82`), host → client

```
type:u8 = 0x82
version:u8 = 1
session_id:u32
token[16]
```

Exactly 22 bytes.

```
token = HMAC-SHA256(key = host_secret, message = "lightray-v1 reset" ‖ session_id:u32)[0..16)
```

`host_secret` is a host-wide secret of at least 32 random bytes, generated at startup
and never sent. The same token reaches the client inside the `RESPONSE`, as `reset_token`, so
a client can recognise a genuine reset without holding any per-session state beyond the
token itself.

The session identifier 0xABCD1234 from the worked example gives:

<!-- vector: handshake.session-unknown -->
```
8201abcd1234d140ab49b93702ca3a56
ea2bafba63e6
```

A host MUST send `SESSION_UNKNOWN` only in response to a protected packet naming a
session it does not have, and only when that packet is **at least 32 bytes**.

A host MUST rate-limit these. A token bucket of capacity 20 refilled at 20 per second,
shared across all destinations, is RECOMMENDED.

> **Why the 32-byte minimum and the rate limit.** The reply is 22 bytes. Without a
> minimum on the trigger, a 16-byte spoofed packet would yield a 22-byte reply and the host
> would become a modest amplifier; requiring 32 makes the reply smaller than the packet that
> caused it. The rate limit bounds what a spoofing attacker can extract in aggregate.

A client receiving `SESSION_UNKNOWN` MUST verify that the length is exactly 22, that the
version is 1, that `session_id` matches its current session, and that the token equals the one
from its `RESPONSE`. The token comparison MUST be constant-time.

> **Why constant-time.** The token is a 16-byte secret shared by exactly two parties and
> a byte-at-a-time comparison leaks how much of a guess was right. The packet is
> unauthenticated and can be sent by anyone who can guess a session identifier, so the
> comparison is directly attacker-driven.

If every check passes, the client MUST treat the session as gone and MAY begin a new
handshake immediately. If any check fails, the client MUST ignore the packet.

## Retransmission

A client that has sent an `INIT` and received nothing SHOULD send **the identical datagram**
again after 100 ms, doubling the wait each time to a maximum of 2 seconds. It SHOULD send it at
most 8 times in all, the first included, and give up 2 seconds after the last.

A client MUST NOT generate a new ephemeral key for a retransmission. The host's cache is
keyed on the datagram, so an identical retransmission is what produces the cached reply.
