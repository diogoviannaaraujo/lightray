# The handshake

One round trip establishes a session: the client sends `INIT`, the host replies with
`RESPONSE`, and both sides derive the same traffic keys. There is no second round trip
and no negotiation beyond what those two packets carry.

The application supplies, out of band, a **pairing identifier** (`u64`) and a
**pre-shared key**. The pairing identifier is not secret; it tells a host which key to
try. The pre-shared key MUST be at least 32 bytes and MUST be generated by a
cryptographically secure random source.

> **Why a pre-shared key at all.** The two endpoints belong to the same person and were
> introduced once, in an application flow this protocol does not define. Given that, a
> certificate chain buys nothing that a pairing secret does not, and costs a round trip
> and a trust store. The PSK also authenticates the very first packet, which is what
> lets the host reject unpaired traffic before doing any asymmetric work.

## INIT (`0x80`), client → host

```
type:u8 = 0x80
version:u8 = 0
reserved:u16                        written 0, ignored on receipt
pairing_id:u64
client_ephemeral[32]                X25519 public key
--- the 44 bytes above are cleartext and are the AAD ---
ciphertext[...]
tag[16]
```

The datagram MUST be **exactly `max_datagram_size` bytes**, the size the client proposes
in its parameters. The sender MUST set don't-fragment on the socket.

A host MUST discard an `INIT` whose total length does not equal the
`MAX_DATAGRAM_SIZE` its parameters declare, and MUST discard one outside the 256–9000
range before attempting to decrypt.

> **Why the padding and the size check.** Two jobs at once. The padding makes the
> `RESPONSE` smaller than the packet that triggered it, so an attacker who spoofs a
> source address cannot use the host as an amplifier. And because the datagram is sent
> with don't-fragment at exactly the size the session will use, a path that cannot carry
> that size fails here — during a retried handshake — rather than after the session is
> up, where it would present as unexplained total loss of large frames.

### Sealed plaintext

```
params_len:u16
params[params_len]                  handshake parameter TLVs
padding[...]                        zero bytes to the end of the plaintext
```

The plaintext is `max_datagram_size − 44 − 16` bytes. The padding is inside the seal and
is therefore authenticated.

> **Why the padding is inside the seal.** Padding appended after the tag would be
> unauthenticated: an attacker could strip it, and a receiver could not tell where the
> ciphertext ended without a length field to trust. Inside, the ciphertext length is
> implied by the datagram length, and any tampering with the padding breaks the tag.

A receiver MUST verify that `params_len` does not exceed the remaining plaintext, and
MUST ignore every byte after `params`.

### The key that seals the INIT

The `INIT` body is sealed with a key derived from the pre-shared key alone, since no
Diffie-Hellman result exists yet.

```
init_context = "lightray-v0 init" ‖ version:u8 ‖ pairing_id:u64 ‖ client_ephemeral[32]
init_salt    = SHA256(init_context)
init_keys    = HKDF-SHA256(ikm = psk, salt = init_salt, info = "lightray-v0 init", L = 28)

key = init_keys[0..16)
iv  = init_keys[16..28)
```

The nonce is the IV itself, because this key protects exactly one packet.

> **Why version and pairing_id are in the derivation.** They are already authenticated
> as AAD, so this is redundant against tampering. It is not redundant against confusion:
> binding them into the key means an `INIT` cannot be replayed into a different protocol
> version or a different pairing even by an implementation that neglects to check the
> AAD, and it costs one hash.

## RESPONSE (`0x81`), host → client

```
type:u8 = 0x81
version:u8 = 0
session_id:u32                      chosen by the host, MUST NOT be 0
host_ephemeral[32]                  X25519 public key
--- the 38 bytes above are cleartext and are the AAD ---
ciphertext[...]
tag[16]
```

The sealed plaintext is the parameter TLVs directly: no length prefix and no padding,
because the length is implied by the datagram.

A `RESPONSE` MUST NOT be larger than the `INIT` that triggered it, and a host MUST
enforce this before sending.

### Key schedule

```
transcript     = SHA256(entire INIT datagram ‖ RESPONSE[0..38))
dh             = X25519(own ephemeral private, peer ephemeral public)
traffic_prk    = HKDF-Extract(salt = transcript, ikm = psk ‖ dh)

response_keys  = HKDF-Expand(traffic_prk, "lightray-v0 response", 28)
c2h_keys       = HKDF-Expand(traffic_prk, "lightray-v0 client",   28)
h2c_keys       = HKDF-Expand(traffic_prk, "lightray-v0 host",     28)
```

Each 28-byte output splits as `key = out[0..16)`, `iv = out[16..28)`.

The `RESPONSE` body is sealed with `response_keys` at packet number 0. Protected traffic
begins at packet number **0** in each direction, under `c2h_keys` and `h2c_keys`
respectively.

> **Why the RESPONSE gets its own key.** It would be possible to seal the `RESPONSE`
> with the host-to-client traffic key and start traffic at packet number 1. That works
> only as long as every implementation remembers to skip packet number 0 — and an
> implementation that starts at 0 reuses a nonce under a key that is also protecting
> real media, which is the one failure in AES-GCM from which nothing can be recovered.
> A separate key removes the possibility rather than documenting it, at the cost of one
> HKDF expansion per session.

> **Why the transcript is the raw datagram bytes.** Hashing the packets as sent, rather
> than a structure rebuilt from parsed fields, means the transcript covers everything —
> the ciphertext, the padding, the reserved bytes, fields a future version adds that
> this one skips. Two peers that parsed the same bytes differently will derive different
> keys and fail immediately, instead of disagreeing later about something subtler.

## Parameters

### What a host accepts

A host MUST NOT accept a capability it cannot honour. In version 0 a host MUST clear
`INTRA_REFRESH` and `FEC` from whatever the client offered, and MAY accept `LTR`.

`MAX_DATAGRAM_SIZE` in the `RESPONSE` MUST be less than or equal to the value the client
proposed. It MUST match the value inside the `CONFIGURATION` TLV; a receiver MUST reject
a handshake where they differ.

The `STREAM_TABLE` in the `RESPONSE` is authoritative. A client MUST use it, not the
table it proposed.

### Stream table entries

Each entry is 4 bytes: `id:u8, kind:u8, direction:u8, class:u8`. Values are in
[registries.md](registries.md).

A receiver MUST reject the handshake if the table is empty, has more than 32 entries,
contains `id = 0`, contains a duplicate `id`, or names an unassigned kind, direction or
class.

> **Why a hard failure rather than skipping the entry.** A stream table both sides do
> not agree on exactly is worse than no session. Skipping an entry one side did not
> understand means the two ends silently disagree about what stream 4 is, and the first
> symptom is media arriving on a stream the receiver treats with the wrong class.

Stream 0 is never listed and is always a bidirectional `RELIABLE` control stream.

### Validation

A receiver MUST reject the handshake if a TLV type in the range 1–8 appears more than
once, if any of types 1, 3, 4 and 5 is absent, if `TIMESTAMP` appears in a `RESPONSE`,
or if `RESET_TOKEN` is absent from a `RESPONSE` or is not exactly 16 bytes.

A receiver MUST skip a TLV whose type it does not recognise, using its declared length.

## Replay protection

`TIMESTAMP` is Unix time in seconds. A host MUST reject an `INIT` whose timestamp
differs from its own clock by more than 30 seconds.

A host MUST additionally keep a cache of recently accepted `INIT` packets, keyed on
`SHA256(entire INIT datagram)`, holding at least 1024 entries for at least 60 seconds.

On receiving an `INIT` whose digest is already in the cache, a host **MUST resend the
identical `RESPONSE` it sent the first time**, and MUST NOT create a second session.

> **Why the cached RESPONSE, and not a rejection.** A client that receives no
> `RESPONSE` cannot tell whether its `INIT` was lost or the reply was, so it retransmits
> the same `INIT` — the same bytes, the same ephemeral. A host that treats the repeat as
> a replay and drops it makes a lost `RESPONSE` unrecoverable: every retry is dropped
> for the same reason, and the handshake never completes on a link that drops one
> packet. Replaying an `INIT` must not create a session; it must reproduce the answer.
>
> The cache is also what makes the timestamp window safe to keep short. The window bounds
> how long a captured `INIT` is useful at all; the cache ensures that within the window a
> repeat is answered rather than acted on.

A host MUST perform this check only **after** the `INIT` authenticates, so that
unauthenticated traffic cannot evict cache entries.

A host SHOULD bound the number of concurrent sessions and MUST have some limit.

## Version mismatch

A receiver that sees an unimplemented version MUST silently discard the packet and
SHOULD count it. It MUST NOT reply.

## Resuming an existing session

A client MAY include `RESUME_SESSION_ID` in its `INIT`, naming a session it previously
held. If the host still has that session, it is parked, and it belongs to the same
pairing, the host MAY adopt it: the session identifier, stream table, configuration and
accumulated statistics survive, while the keys and the packet-number space are replaced
by the ones this handshake derives.

If the host does not adopt it, it allocates a new session identifier and the client
starts fresh. The client learns which happened from the `session_id` in the `RESPONSE`.

Details of parking and the grace window are in [reconnect.md](reconnect.md).

## SESSION_UNKNOWN (`0x82`), host → client

```
type:u8 = 0x82
session_id:u32
token[16]
```

Exactly 21 bytes.

```
token = HMAC-SHA256(key = host_secret, message = session_id:u32)[0..16)
```

`host_secret` is a host-wide secret of at least 32 random bytes, generated at startup
and never sent. The same token is delivered to the client inside the `RESPONSE` as
handshake TLV 8, so a client can recognise a genuine reset without holding any
per-session state beyond the token itself.

A host MUST send `SESSION_UNKNOWN` only in response to a protected packet naming a
session it does not have, and only when that packet is **at least 32 bytes**.

A host MUST rate-limit these. A token bucket of capacity 20 refilled at 20 per second,
shared across all destinations, is RECOMMENDED.

> **Why the 32-byte minimum and the rate limit.** The reply is 21 bytes. Without a
> minimum on the trigger, a 16-byte spoofed packet yields a 21-byte reply and the host
> becomes a modest amplifier; requiring 32 makes the reply smaller than the packet that
> caused it. The rate limit bounds what a spoofing attacker can extract in aggregate.

A client receiving `SESSION_UNKNOWN` MUST verify that the length is exactly 21, that
`session_id` matches its current session, and that the token equals the one from its
`RESPONSE`. The token comparison MUST be constant-time.

> **Why constant-time.** The token is a 16-byte secret shared by exactly two parties and
> a byte-at-a-time comparison leaks how much of a guess was right. The packet is
> unauthenticated and can be sent by anyone who can guess a session identifier, so the
> comparison is directly attacker-driven.

If all three checks pass, the client MUST treat the session as gone and MAY begin a new
handshake immediately. If any check fails, the client MUST ignore the packet.

## Retransmission

A client that has sent an `INIT` and received nothing SHOULD retransmit **the identical
datagram** after 100 ms, doubling the interval on each attempt to a maximum of 2 seconds,
giving up after 8 attempts.

A client MUST NOT generate a new ephemeral key for a retransmission. The host's cache is
keyed on the datagram, so an identical retransmission is what produces the cached reply.
